# 05 – HTTP contract

*PLAN.md §9-11*

The plan fixes exactly what responses look like, so a client can rely on the status code, headers and body shape.

## Collection envelope

```json
{
  "data": [],
  "count": 773,
  "limit": 50,
  "offset": 0,
  "next": "/solar/v1.0/installations/{id}/readings?sort=-timestamp&limit=50&offset=50",
  "previous": null
}
```

- `count` = all matches the caller may see, after filters and before paging.
- `next` and `previous` keep every filter and the sort order; they are `null` at either end.
- Single resources are returned directly, without an envelope. `null` means "absent", never an invented zero.

## Status codes

| Code | When | Extra |
|---:|---|---|
| 200 | Read or replacement succeeded | `ETag`; `Last-Modified` where reliable |
| 201 | Reading or installation created | `Location`, `ETag`, `Last-Modified`, `Content-Location` |
| 204 | Installation deleted (**Changed:** plan said 200) | no body |
| 304 | Conditional GET, nothing changed | empty body |
| 400 | Bad JSON, field, id, filter or query | |
| 401 | Missing, invalid or expired token | `WWW-Authenticate: Bearer` |
| 403 | Valid token without the scope; or PUT/DELETE without `If-Match` | |
| 404 | Not found **or** outside your area (identical) | |
| 405 | Method not supported | `Allow` |
| 406 | Client refuses JSON | |
| 409 | Duplicate reading; history-protected delete or change | |
| 412 | `If-Match` out of date | no write happened |
| 413 / 415 | Body too large / not JSON | |
| 500 / 503 | Unexpected error / database unavailable | no SQL or stack trace |

Errors generated by Vercel itself, before or after the function runs, cannot use the API error body. This is a known limitation.

**Content negotiation:** JSON only. A missing `Accept`, `*/*` or `application/json` all work. `q` values are parsed properly: `application/json;q=0` → 406, while an `Accept` listing XML *and* JSON still succeeds. POST and PUT need a JSON `Content-Type`, otherwise 415.

## One error body everywhere

**Changed:** the plan sketched `{code, message, details[{field, reason}], request_id}`. The build uses G §11's field names:

```json
{
  "code": 1001,
  "message": "Request validation failed",
  "description": "Bad request",
  "error": [
    { "code": 1001, "field": "power_kw", "message": "Too small: expected number to be >=0" }
  ],
  "request_id": "3f1c2b7e-…"
}
```

| Field | Meaning |
|---|---|
| `code` | Stable product code. The HTTP status is not enough: one 401 can be 1010 (no token) or 1011 (bad token) |
| `message` | Human-readable sentence |
| `description` | The HTTP status name |
| `error` | Only on validation errors: one item per invalid field |
| `request_id` | Trace id, also sent as the `x-request-id` header |

Code catalogue (`src/http/errors.ts`): 1000 internal · 1001-1004 validation/JSON/query/path · 1010-1011 authentication · 1020-1021 scope / `If-Match` required · 1030-1031 not found / no route · 1040 method · 1050 not acceptable · 1060-1063 conflicts · 1070 stale `If-Match` · 1080 too large · 1090 media type · 1100 unavailable.

An error never reveals another area's labels or counts, tokens, keys, connection strings or stack traces.

## History queries

| Parameter | Meaning |
|---|---|
| `province-id`, `district-id`, `substation-id` | Narrow by area; must be consistent with each other |
| `from` | Inclusive start (RFC 3339 with offset) |
| `to` | Exclusive end; must be after `from` |
| `sort` | `timestamp` (oldest first) or `-timestamp` (newest first, default) |
| `limit` | 1-100, default 50 |
| `offset` | 0 or more, default 0 |

**Changed:** the plan wrote `province_id`, `as_of` and so on. They were hyphenated because G §5.1 rejects underscores and the rubric says "throughout".

**What a caller sees** = their area ∩ the path ∩ their filters ∩ the time window. Filters can only narrow:

| Situation | Result |
|---|---|
| Filter on someone else's area | 200, empty `data`, `count: 0`, null links |
| Path to someone else's item | 404 |
| Contradictory filters (a district not in the given province) | 400 |
| Installation exists but has no readings | 200, empty envelope |
| Offset past the end | Empty page, correct `count` |
| Unknown or malformed parameter | 400 (never silently ignored) |

Sort values are mapped to fixed SQL fragments, never pasted in. The reading id breaks timestamp ties, so pages never overlap.

**Why offset paging:** G §10.3 teaches it. Its weakness is that new readings arriving between requests can shift pages; use a fixed `to` for reproducible paging. Cursor paging is the future alternative.

## Caching: ETag and Last-Modified

- Every successful GET has a **strong ETag**, the SHA-256 of the exact JSON sent. Collections, overviews and the summary are included.
- `If-None-Match` → 304 with an empty body, **only after** the login and area checks. It takes precedence over `If-Modified-Since`.
- `Last-Modified` appears only where one reliable time exists: installations (`updated_at`) and readings (`received_at`). Composites and collections depend on many rows, so they carry an ETag only.
- Authenticated responses use `Cache-Control: private, no-cache` and `Vary: Authorization, Accept`, so no shared cache serves one analyst's data to another. ETags are performance hints, never credentials.

## Concurrency: If-Match

- PUT and DELETE on installations require `If-Match` with the current ETag.
- The version check and the write happen together, under a row lock. Of two simultaneous edits with the same ETag, one gets 200 and the other 412.
- Missing `If-Match` → 403 (code 1021), matching G §9's own example, rather than RFC 6585's 428.
